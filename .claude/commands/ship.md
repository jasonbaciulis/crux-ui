Commit the working changes, bump the package version, create a pull request to main, merge it when CI passes, and create a GitHub release. The release triggers `.github/workflows/release.yml`, which publishes the new version to npm.

Running this command is my explicit request to stage, commit, push, merge and release.

## Check the package

1. Run `bun run format:check && bun run lint && bun run test && bun run build`. If any step fails, stop and report the failure. Do not commit, push or release.

## Branch & commit the working changes

If `git status` shows no uncommitted changes and `git log main..HEAD` shows no commits, skip to "Choose the version".

2. Run `git status` and `git diff` to understand all uncommitted (staged and unstaged) changes.
3. If the current branch is `main`, create and switch to a new release branch: `git switch -c release/<short-descriptive-slug>` (kebab-case, derived from the overall theme of the changes). If the current branch is not `main`, stay on it and use it as the release branch.
4. Group the changes into logical commits — one commit per coherent unit of work, based on which files changed and what was changed together (e.g. a feature, a bugfix, a refactor, a config change should each be their own commit). Stage each group explicitly with `git add <paths>` rather than `git add .`.
5. Write each commit message following the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) spec:
   - Format: `<type>[optional scope]: <description>` — e.g. `feat(accordion): add hidden-until-found support`.
   - Common types: `feat`, `fix`, `refactor`, `chore`, `docs`, `style`, `test`, `perf`, `build`, `ci`.
   - Keep it brief: a single sentence, lowercase, no trailing period — a clean one-liner in the GitHub UI.
   - Use `!` after the type/scope (e.g. `feat!:`) for breaking changes. See "Public contract" below for what counts as breaking.
   - Do not add a body or footer unless a change is genuinely breaking or needs context.
   - Do not mention it's generated by Claude.

## Choose the version

npm reads the version from `package.json`, not from the tag, so the bump goes into the pull request.

6. Read the current version from `package.json` (`node -p "require('./package.json').version"`) and the published version (`npm view crux-ui version`). If they differ, stop and ask me which one is correct.
7. Read the commits since the latest tag (`git log $(git describe --tags --abbrev=0 main 2>/dev/null || echo main)..HEAD --oneline`; with no tag yet, read `git log main..HEAD --oneline` and the uncommitted diff). Recommend a bump based on the "Public contract" below, then ask me to confirm:
   - While the version is `0.x`: a breaking change or a new primitive, part, attribute, event or magic is **minor**, a fix is **patch**. Recommend **major** (`1.0.0`) only when I say the API is stable.
   - From `1.0.0`: breaking is **major**, a new primitive, part, attribute, event or magic is **minor**, a fix is **patch**.
8. Bump the version without a tag: `npm version <major|minor|patch> --no-git-tag-version`. Commit it alone: `git add package.json && git commit -m "chore(release): vX.Y.Z"`.

## Create the pull request

9. Run `git log main..HEAD --oneline` to see the commits on this branch.
10. Run `git diff main...HEAD --stat` to see changed files.
11. Push the current branch: `git push -u origin HEAD`
12. Create a PR to main using `gh pr create --base main`. Write a concise title (under 70 characters) and a short description summarizing the changes. Use this format for the body, and leave out a section that has no bullet points:

```
## What's new
<bullet points>

## What's fixed
<bullet points>
```

Don't include anything else. Don't mention it's generated by Claude.

13. Return the PR URL.

## Merge the pull request

14. Wait for CI on the PR: `gh pr checks --watch --fail-fast`. If it reports no checks yet, wait a few seconds and run it again. If a check fails, stop and report which step failed. Do not merge.
15. Merge the PR into main: `gh pr merge --merge` (wait for it to complete). This ensures the version bump is on `main` before the release is tagged.
16. Switch back to main and pull the merged changes: `git switch main && git pull`.
17. Delete the merged branch locally and on the remote: `git branch -d <branch> && git push origin --delete <branch>`.

## Create the release

18. Create the release with `gh release create vX.Y.Z --target main --title "vX.Y.Z"`, using the version from step 8. Use the same body format as the PR, covering all changes since the previous release.
19. Return the release URL.

## Check npm

20. Find the publish run: `gh run list --workflow=release.yml --limit 1`. Watch it: `gh run watch <run-id> --exit-status`. If it fails, report the failed step and tell me the release tag exists but npm has no new version. Do not delete the release or the tag.
21. Check that npm has the new version: `npm view crux-ui version`. Return `https://www.npmjs.com/package/crux-ui/v/X.Y.Z`.

## Public contract

The public contract for semver (from CLAUDE.md) — a change to any of these is breaking:

- Directive and part names (`x-accordion`, `x-accordion:trigger`).
- Config attributes (`default-open`, `multiple`).
- `data-*` attributes and CSS variables.
- Event names and their `detail` payloads.
- Magic APIs (`$accordion`) and `x-model` value types.
- The package `exports` entries and the minimum `alpinejs` peer version.

Files in `src/core/` and internal DOM manipulation are not public API, so changes there are patch or minor by their effect.
